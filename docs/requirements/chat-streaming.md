> 所属板块：对话渲染（chat-streaming）。本档为首篇。

## 1. 模块目标

让**流式回复期间的界面保持跟手**：模型每吐一个字，只重建与该字相关的部分，界面开销不随对话变长而增大。今天是反过来的——每个增量都重算整棵历史，所以长对话越聊越涩。折叠只隐藏过程，不隐藏用户要看的结果（跨回合同样）。

## 2. 事实基线（2026-10-17 实读）

- 每收到一个文本增量，`lib/chat/chat_session.dart:159-163` 通知一次；`lib/chat/chat_history_view.dart:1214` 随 `setState`。
- `build` 里 `_built = null`（`chat_history_view.dart:2090`），整棵历史重算（含 `cacheExtent: 900` 内的行，`:2219`）；流式时约 **20–60 次/秒**。
- 同频连带开销：折叠整体重算（`step_folds.dart:65-70`，成本 ∝ 会话条目总数）与流式消息 markdown 整篇重解析（`markdown_view.dart:83-98`，长回复退化为 O(L²)）。**图片收集 `_images`（`chat_history_view.dart:2122`）不是每增量成本**：它只作为 `ChatImages.all` 的回调传入，打开图库时才按需调用一次（O(N)）——缓存要防的是重复按需收集。
- 已做对的地方（本批不得破坏）：列表已虚拟化（`SuperListView.builder:2214`）；非流式 markdown 有缓存（`markdown_view.dart:69-98`）；折叠隐藏行按实例记忆化（`chat_history_view.dart:1763-1793`）。

## 3. 功能点

**F1 流式增量只重建该重建的部分**：一个文本增量到达时，重建范围不随历史长度增长——外壳（滚动条主题、选择区、骨架容器）不进入每增量的重建路径，只有正在流式的那一条**（思绪连跑合并显示时，为它所在的那一行）**及其必要的布局参与。

验收（可机检）：同一段固定脚本回放（120 个增量、每段 8 字）下逐次计数——**`ChatFindRow` 重建 0 · `SuperListView` 0 · `SelectionArea` 0 · `ChatItemView` 恰 1**；且**20 回合与 200 回合两种历史下逐项相等**；**文本确实在更新**——回放过程中 `MarkdownView` 收到的输入数据每次都是最新全文（渲染块可按 F3 的节流节奏），回放结束后可见文本与一次性写入的全文一致。改前 / 改后同法各给一份读数（改前必须实测，不得估）。

**F2 折叠不再全量重算；图片集合不重复收集**：尾部增量只重算受影响的那一回合；图片集合按「条目数 + 末条身份」缓存（防的是打开图库时的重复 O(N) 收集，不是每增量成本）。
验收（可机检）：① 增量回放期间，折叠计算次数不随历史长度线性增长，且与全量计算逐项相等（对拍）；② 同一历史下连续多次取图片集合 ⇒ 实际收集次数为 1（缓存命中）。

**F3 流式 markdown 不做整篇重解析**：按块缓存（只解析末尾未闭合块）或节流（≥50ms）二选一，由设计定；选节流须证明不会丢失最终态。
验收（可机检）：长回复（≥5000 字符）流式期间，该消息的解析次数上界可数；流式结束后渲染结果与一次性解析完全一致。

**N1 基线可复现**：本批必须给出**同一脚本、同一台机器**上的改前 / 改后读数（构建次数、解析次数；可选附加帧耗时）。

**F5 大会话流式时，重绘范围不随界面大小与历史长度增长**：一条文本增量到达，GPU 光栅化的代价只与**实际改变的那一块**成正比，不与整块画布、也不与已有渲染对象总数成正比。

事实基线（2026-10-26 实读，Release 1.7.2+19，窗口 3840×2088@1.5 = 逻辑 2560×1392）：会话 1060–1205 条、渲染对象 6163–6589 时，**每帧 raster 340–350 ms 而 build 仅 0–9 ms**——慢在光栅化，不在构建。四条慢帧**全部发生在流式中**。

验收（可机检）：同一回放场景下，`timing.rasterDuration` 的超预算帧（阈值由设计定，建议 100 ms）由当前值降到 **0**；且总帧数与改前同量级（不得靠减帧达成）。

**F6 窗口不可见时不渲染，切回时一次追平**：应用窗口失焦（`lifecycle inactive`）期间不产生渲染帧；重新聚焦后一次重绘到最新状态，期间到达的增量不得丢失。

事实基线（同上实读）：失焦期间仍持续出帧——四条慢帧中 **3 条的状态字段为 `inactive`**，即用户看不见时仍在按 ~350 ms/帧光栅化；用户感知到的停顿发生在**切回窗口后的那一帧**。

**GPU 占用基线（2026-10-26 01:40 实读，本机 Intel Arc 130T 集成显卡，3840×2088 画布）**：窗口失焦时 baocode 仍占 **30.6–30.7%** GPU（三次采样稳定），系统总占用 ~40%，`dwm` 12.5%。⇒ 本机 GPU 余量本就紧张，常态 30% 的无效重绘把它吃光；流式时冲到 90%+ 就是卡顿的直接来源。

验收（可机检）：① 失焦 60 秒期间渲染帧数为 0（或仅保活帧）；② **失焦时 baocode 的 `GPU Engine` 占用接近 0%**（同机同窗口，失焦前后各采样 3 次取均值对比）；③ 聚焦后 1 帧内呈现失焦期间到达的全部内容；④ 流式输出在失焦期间**不丢内容**（结束时可见文本与全文一致）。

**N2 两批读数同法可比**：F5 / F6 的改前与改后，必须用**同一场景、同一窗口尺寸、同一机器**测；改前读数须在动代码前量（设计阶段给出量法，优先复用 `tool/perf` 的既有场景）。

**F8 创建进程不得阻塞窗口线程**：thincoder 内核的**两处**进程创建点（内核自起（含启动时逐项目列会话）与设置页版本探测）不得让窗口线程（Flutter 的 platform/UI 线程）停止处理消息。**本批验收档 = 500 ms**（N4 的量具粒度就是 250 / 400 ms，500 ms 为可机检阈值）；**50 ms 是长期目标，本批无量具，另计**。git / LSP / forge 等低频路径**保持上游原样**，不在本批迁移面内（将来 `[stall]` 指向哪条再迁哪条）。

事实基线（2026-10-26 02:10，Windows 自带挂起看门狗的 9 份报告）：**8 份**的窗口线程栈停在 `ZwCreateUserProcess ← CreateProcessInternalW ← CreateProcessW`，另 1 份停在 `ZwQueryValueKey ← BasepQueryAppCompat`（同属进程创建内部的兼容性检查）。报告原文：`The windows' thread took no message for 6 s`。⇒ 用户感知的"卡 6 秒"即此。

验收（可机检）：同一操作路径下，挂起看门狗不再产出 6 秒报告（`logs/hangs/hang-*.txt` 零新增）；`[stall]`（N4）不再记录 > 500 ms 的窗口线程停顿。

**N3 DPR 变化留痕（诊断，先量后定）**：窗口的设备像素比（`devicePixelRatio`）每次变化时写一行 `[viewport] view <id> dpr <旧> -> <新> size <逻辑宽×高>`，带时间戳。**只在 DPR 变化时写**；仅尺寸变化不写（`[views]` 行已承担尺寸变化，两条并存、互不替代）。
事实基线：本机三显示器、**同时存在 1.5 与 2.25 两种缩放**；用户报告"界面突然放大占满屏幕、约 2 秒后缩回"，而现有日志里 view 0 恒为 `@1.5`、**无任何 DPR 变化记录**。
验收：真机重现一次放大现象时，日志能给出变化前后的 DPR 值与时刻（有则定位、无则排除这条假设）。

**N4 停顿看门狗：界面线程被卡住时必须留下读数**：在 UI isolate 上挂一个固定周期的计时器（建议 250 ms）；实测两次触发之间的间隔，超过阈值（建议 400 ms）就写一行 `[stall] gap <N> ms; <当时的界面状态>`。**`gap` 的定义 = 实测间隔 − 周期**（超出那一段），这样 800 ms 的同步阻塞读作 750–800 ms，落在验收窗口内。理由：界面线程被同步工作堵住时**连一帧都画不出来**，现有 `[slow]` 帧埋点因此零记录——用户侧的"莫名其妙卡住"正是这个缺口。

事实基线：2026-10-25 22:00–23:15 用户三次报告卡顿，同期 `[slow]` **零条**；`errors.log` 零条；Windows 事件、崩溃转储、内存耗尽、GPU TDR **全部为空**。⇒ 现有观测面看不到这一类停顿。

验收（可机检）：构造一次 UI 线程 800 ms 的同步阻塞（测试内 sleep 亦可），`[stall]` 行必须出现且 gap 落在 700–1000 ms 之间；无阻塞时 1 小时内 `[stall]` 行数为 0（不得误报）。

**N5 已有的事故证据必须被看见**：应用启动时检查 `<数据目录>/logs/hangs/`，若存在比上次启动更新的挂起报告，写一行日志 `[hang] N new reports since <时间>（路径）`，并在诊断入口提供可点击的路径。理由：`hang_watchdog` 一直在正常产出报告，但**没有人知道它们存在**——2026-10-26 夜间 9 份带完整线程栈的报告在 `logs/hangs/` 里躺了三个小时，期间用户与代理都在"猜"。

事实基线：`%APPDATA%\baocode\logs\hangs\` 现有 9 份 `hang-*.txt` + `.dmp`（2026-10-25 20:54–23:44），`events.log` 与 `errors.log` 里**零条**提示它们存在。

验收（可机检）：预置一份新报告后启动应用，日志出现 `[hang] 1 new reports`；无新报告时零提示（不得误报）。


**F4 折叠按回合分界，跨回合不吞答案**：完成回合的工作折成一行，但只折**本回合自己的** work、折到**本回合自己的答案之前**；unprompted 回合（子代理回调后主 agent 自动续写）是独立回合，它自己的 work 可折、答案保留，上一回合的答案不得被折走。

验收（可机检）：用户回合回答 + unprompted 回合回答并存时，两条答案都可见；上一回合的 work 仍折成一行；子代理回调汇报落地后，上一回合答案不被折走；单回合内「中间回答被折」的既有语义不变；既有性能读数（六类外壳 0/0、`ChatItemView` 每增量 1、A4 恰 1 帧）不回退。

边界：只改折叠的回合边界；不改 unprompted 回合语义、折叠视觉形态、粘顶/选择区/滚动锚定；不改事件形态（`KernelEvent` / `Transcript`）。重载后旧回合仍按提示词规则（退化，用户 2026-10-18 接受，另批再议）。

## 4. 边界（明确不做）

- 不改视觉与交互：粘顶消息、跨重建的选择区、滚动锚定（`_BeforeLayout` / `_StickyFollower`）、`cacheExtent` 语义保持。
- 不改数据模型（`ChatSession` / transcript 的事件形态零动）。
- **内核侧允许改的部分**：`lib/platform/**` 及既有 `Process.*` 调用点（进程创建挪入代理 isolate），含 thincoder 适配层里发起进程的那几处（`thincoder_process_io.dart` / `thincoder_locator.dart` / `thincoder_catalog.dart` / `thincoder_lifecycle.dart` / `thincoder_release.dart` 等）。**内核的语义面不改**——ACP 协议、事件形态、会话模型一律零动；F8 只搬"在哪里创建进程"，不改"创建什么、怎么通信"。
- **删除预热池**：把 `lib/kernel/thincoder/thincoder_warm.dart` 整档删除，并清掉它的挂点（`thincoder_lifecycle` 的领池分支、`thincoder_kernel` 里的池字段与领池判断、`workspace` 的预热调用、`events.log` 的 `timing: warm hit/miss` 行），回到上游 Claude 内核的形态——每会话一个进程、用完关闭。理由：它今天 0 命中（34 miss / 0 hit）、净亏；与其生命周期（TTL / keep / release）带来的复杂度相比，省的 0.6–1.5 s「准备中」不值。**验收**：`lib/**` 与 `test/**/*.dart` 里 `thincoder_warm` / `warm hit` / `warm miss` / `预热池` 零命中（**代码面**；索引与文档里的描述性文字不计，`warmWindow` / `warmUp` 这类同名不同义不算）；且开关会话仍正常（每次开会话一个进程、用完释放）。
- 不引入新依赖、不换列表实现（`SuperListView.builder` 保留）。
- 不做整档重构：`chat_history_view.dart` 若必须拆，**只拆本批需要的那一小块**，并在设计里写明行数预算。
- 不动非流式路径的既有缓存策略。
- **F5/F6 不做列表虚拟化与分段上限**：超大会话（1000+ 条）的结构性优化另立一批；本轮只改重绘边界与出帧时机，不改列表实现、不改数据分页。
- **不换渲染引擎**：Impeller 保持（`tool/engine` 打补丁那份）；不以"退回 Skia"作为达标手段。
