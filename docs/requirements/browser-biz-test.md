## 2. 模块目标（一句）

在 Chrome 上跑完整条航运业务线，并把**预期结果**与**用例来源（新/旧代码）**落到盘上而不是靠模型记忆，一轮跑完出一份可复验的问题清单。

## 3. 功能点（可验收）

- **F1 模式切换**：像 plan 一样可切换的第三种模式（`normal` / `plan` / `btest`），在会话里可见可切换，切换后新回合按该模式执行；退出即恢复。
- **F2 测试模式提示词**：随模式注入的稳定指令（角色、纪律、判定口径、报告格式、禁止项）。用户已有草稿（`~/.thincoder/skills/browser-biz-test/SKILL.md`），本批把它收敛为**模式内建**的提示词。
- **F2.1 操作方式 = 模拟真人**（用户 2026-10-23 00:01 定）：
  - **入口只一次**：全场只允许**起始那一次** URL 导航；之后所有页面跳转一律点菜单 / 链接 / 按钮完成，**禁止手输深链**。
  - **按看得见的文字定位**：用按钮文字、字段 label、表头列名、可见角色定位目标；**禁止**以 DOM id / class / xpath / 快照编号作为首选定位手段。
  - **按可见文本找不到可点目标 ⇒ 这本身就是缺陷**（label 未关联 / 可访问性缺失），记入报告，不要绕道用内部标识。
  - **逐字键入**：输入用打字，**禁止**用 JS 直接赋值、改隐藏字段、或绕过表单直接调接口。
  - **读不推进流程**：读接口 / console / DOM 只用于**判定**，不得用来代替点击推进。
  - **唯一例外**：若某步用户本人也无法完成（例：页面没有菜单入口，只能手输 URL —— 既有 issue #899 就是这类），**先记为缺陷**，再用 URL 继续，并在报告里标注「本步绕道」。
- **F3 预期结果持久化（治"忘了预期"）**：每条业务线一份可读文件，存放**步骤 / 操作 / 预期 / 预期出处**；**由 AI 生成与更新**（用户不手写），但格式稳定、可 diff、可回看；跑之前必读，跑完把新增/修正写回。
- **F3.2 落点 = 独立 QA 仓（用户 2026-10-23 01:52/01:53/01:56 定）**：不写进业务仓，**不 git init**。**一个工作区只有一个 QA 根**。派生顺序：① `btest.qaRoot` 有值 ⇒ 用之（非绝对路径则拒绝）；② 否则 `qaRoot = <会话工作区根>/qa`（`repoRoot` 在其下时）；③ 会话工作区根就是业务仓本身（`cwd == repoRoot`）⇒ `qaRoot = <repoRoot 的父目录>/qa`（守住“业务仓不写”）；
  ④ 其余情况同 ③。文件 = `<qaRoot>/<basename(repoRoot)>/<业务线>.md`。实例：工作区 `C:\Users\xinbo\repos` + `repos\v2-booking` ⇒ `repos\qa\v2-booking\订舱.md`；工作区 `C:\Users\xinbo\repos` + `repos\clientA\v2-timecharter` ⇒ **同一个** `repos\qa\v2-timecharter\船期.md`；
  工作区 `D:\work\客户A` + `客户A\repos\v2-booking` ⇒ `客户A\qa\v2-booking\订舱.md`。`btest_run_start` 必须返回解析后的绝对路径，并注明用了哪条分支。业务仓只用于 `git log`（判 `source: new|old`）。
- **F3.1 预期必须有出处（`expectFrom`）**：每条预期都指向它凭什么——业务设计档的**某一节**、冒烟清单的某一条、或某条历史 issue。可信度三级：**强** = 业务设计档明写；**中** = 冒烟清单 / 历史 issue；**弱** = 代码现状。**代码现状不得作为预期来源**——拿实现当预期等于"实现即正确"，所有 bug 会被自动判为正常。报告里每条「预期不符」必须能追到 `expectFrom`。
- **F4 用例来源标注（治"忘了是旧代码生成的"）**：每个 case 标注 `source: new | old` 与出处（提交号 / 需求点名）；新旧差异出现时按「新建前置状态 → 重跑 → 仍不同才报」处理。
- **F5 只读探查**：允许"只跑不写"的一轮（导航 + 快照 + 读接口），产出或修订 F3 的流程文件；不确定时回看业务仓的文档与代码（`api` / `database` / `docs` / 前端仓）。
- **F6 一轮跑完的报告**：表格（业务线 / 步骤 / 现象 / 证据 / 严重度 / 复现前置），**不截图**；末尾单列「阻塞 / 待确认差异 / 本轮未覆盖」。
- **F7 遍历策略开关（用户 2026-10-23 02:26/02:29/02:34 定）**：`btest_run_start` 增加 `traversal`，二值：**`chain`（深度优先）**＝只要有下一步就走下一步，走不动了记一条断点（原因：门控 / 无权限 / 数据不足 / 没有下一步）再找别的路继续；**`surface`（广度优先）**＝把一个界面的每个东西摸完就走到下一个界面，按界面逐个覆盖（详见 F7.2）。
   用户原话：「我只要告诉它尽可能往下一步走，出了问题告诉我，就是深度；尽可能去把整个界面都抹一遍就是广度」。**不是状态机，不要求预列流转表；断点必录且不算失败。**
- **F7.2 广度的范围 = 整个范围，不是一个页面（用户 2026-10-23 03:59）**：`surface` 把一个界面的每个东西摸完（页签 / 按钮 / 表单 / 筛选 / 列表底）**就走到下一个界面继续**，按界面逐个覆盖，直到本轮声明的范围走完；`uncovered` 列的是**范围内没摸到的界面 / 分支**。用户原话：「广度测试并不局限与某一页面，只是这个界面探索完了，再往后走」。
- **F7.1 权重来自本仓历史 issue（用户 02:29「可以结合我们的issue，看看哪里容易出问题」）**：两种模式都按历史缺陷密度排序，实测聚类（`51marine-issue-audit-20261021/issues-v2dev.json`，924 条，标题关键词）：刷新/数据丢失 58 · 报错/异常 52 · 为空/空态 40 · 筛选/查询 35 · 金额/数字 31 · 按钮/交互 24 · 英文/文案 22 · 重复提交 20。`surface` 按此顺序抹面；**每次提交类动作之后必查**刷新丢失 / 金额勾稽 / 重复提交（不绑死流转）。
- **F8 待确认项先出建议、不出判定（用户 2026-10-23 02:26/02:29 定）**：报告中 `expectFrom` 为弱或无来源的项，交付前由一个子代理逐条给**完整建议**——倾向（可能正常 / 可能有问题 / 建议你定）+ 理由（`file:line` 或文档节）+ **优劣势**（误判为缺陷的代价 vs 漏判的代价）。**子代理不得改判定**：报告里这些项仍标「待确认」，判定权在用户（守住 F3.1「弱来源不得判预期不符」）。
- **F9 两个开关，不背参数（用户 2026-10-23 03:34「不能做成按键选择吗」/ 03:35「现在」）**：btest 状态行右侧两个开关——**遍历**（`深度` = chain ／ `广度` = surface）与**写**（`只读` ／ `允许写`）。取值优先级写死：**显式参数 > 会话开关 > 设置缺省**；运行中的状态行显示本 run 的实际值（不是开关位置）。开关与模式的跨重启保留见 **F11**。
  业务线**不做下拉**：`line` 仍由用户的话给出（下拉需先知道 `repoRoot` 才能列业务线，会多一步）。开关与模式的持久化见 **F11**。
- **F10 断点可派只读子代理查明原因（用户 2026-10-23 03:44「加」；派发方式 2026-10-23 19:07 逐字「主代理发现一个，就派一个先出去，否则等主代理都走完慢死了」）**：`chain` 轮走到断点时，派一个**只读**子代理（`explore`）查清「为什么走不动」——按业务仓代码与设计档给出一句结论 + `file:line`。**发现即派、不等答案**：记录断点的同时派出，主代理继续走下一步（等待会把一轮拖成串行）。答案回来时 **run 未结束 ⇒ 写进该断点的 `cause`**；
  **run 已结束 ⇒ 结论进收尾消息**，不重开 run、不阻塞；`cause` 可缺省，迟到的答案不破坏字段形。约束：`reason` 仍是四值枚举（门控 / 无权限 / 数据不足 / 没有下一步），子代理**不改判定、不操作浏览器**；一次 run 最多派 **3** 次（限制的是研判成本，不是等待时间）；不可用 ⇒ `cause = 未查明（<原因>）`，run 照常继续。
- **F11 模式与两个开关要记住（用户 2026-10-23 06:46「A全局btest开工」）**：btest 开没开、遍历选哪档、写选哪档，**全部落全局设置**（ `settings.json` 的 `btest.*` 键，与 `allowHosts` / `prodHosts` / `readonly` / `qaRoot` 同处），**重启后仍然生效**。缺省（键不存在）= 关、`广度`、由 `btest.readonly` 初始化。会话打开时从设置读入；
  点烧瓶 / 点任一开关时写回。**写入失败不阻断 UI**（与设置页其它 btest 键同口径：失败记 `debugPrint`，界面照常变）。
- **F12 人工接管点：只在用户点名「单独测试这个上传功能」时停手；流程中遇到就记下来继续（用户 2026-10-23 20:08 与 20:11 两句定，后者逐字「不要在流程里面停下，只是记住，如果我说单独测试这个上传功能，它打开界面停手，我上传，它判断继续接手；如果是流程中遇到了，记下来继续往下走」）**：
  文件选择框（上传）这类**浏览器内、只能由人完成**的动作，分两种情形，规则不同：
  - **情形 A：用户点名单独测这个功能**（如「单独测试一下上传」）⇒ agent 把界面打开到那一步、**停手**，说一句要传什么，**等用户做完再说"好了"**，然后读附件列表与单据快照（P07）判定，继续接手后面的步骤。
  - **情形 B：整条流程跑到上传这一步** ⇒ **不停**。记下「该步骤需要人工上传、本轮未执行」，**继续走后面的步骤**，报告里把它列成需要人工补测的一步（进 `uncovered`，不是断点、不算失败、不占研判上限）。
  - **两种情形共同的禁令**：不点 `input[type=file]`（点了也是空对话框）、**不写临时文件充数**、不调接口绕过界面。
  - **判据 A**：对话里出现明确的"请你在这里选文件上传"，界面停在原地；用户说"好了"后 agent 读附件列表 + 单据快照并继续，报告该步骤带用户提供的文件说明。
  - **判据 B**：流程没有被上传卡住（后续步骤照常走完），报告 `uncovered` 里点名该界面/该步骤"需人工上传"。
  - **本批的实测缺陷记录**：agent 曾尝试写 `.thincoder/tmp/btest-attach-*.txt`（父目录不存在 ⇒ `PathNotFoundException` 原文外泄进对话）与 `%TEMP%`（被路径守卫正确拒绝）——**根因是缺这两条路**：既没告诉它"没人会替你上传"，也没告诉它"没让你停就别停"。




## 4. 边界（明确不做）

- **不改业务代码、不改数据库**；**不提交工单**（"可能涉及提交 issue"留二期，且需单独授权）。
- **不截图**（用户明确不要）；**不边走边停**（发现问题记录后继续，除非整轮无法继续）。
- 不在生产环境做写操作（用户未授权生产；默认为测试环境）。
- 不替代人工复验：报告是给用户复验用的清单，不是结论。

## 5. 验收（可机检 / 可走查）

1. 模式切换可见可恢复：切到 `btest` 再切回 `normal`，会话行为随之改变，且不残留提示词。
2. 跑一条业务线（`v2-booking` 订舱）产出 F6 表格，且**每条问题的证据可复核**（接口路径+状态码 / console 原文 / 字段前后值）。
3. **预期来自盘上且带出处**：报告里每条"预期不符"能指到 F3 文件的某一行（而不是"模型认为"），且该行的 `expectFrom` 指到具体业务设计档的节 / 冒烟清单条目 / issue 号；`expectFrom` 指向代码现状的条目**不得**判为「预期不符」。
4. **来源可追溯**：每个 case 带 `source` 与出处；差异处置路径在报告里可见。
5. 稳定性读数：同一业务线连续两次只读跑，步骤序列一致率可报（用于后续改进，不作为本批硬门槛）。
6. **操作真实性（F2.1）可机检**：一轮跑完，下列读数全部成立。

   ① **入口动作**（`browser_navigate` / `browser_act` 的 navigate 步 / `browser_open`）次数 = 1（仅起始）；
   其余入口动作必须带 `detour`，且 **`detour` 计数 = 报告「绕道」行数**。

   ② `browser_evaluate` 无写值调用；`browser_request` 的 `replay` 调用 = 0。

   ③ 所有 `browser_click` / `browser_type` 的目标都以可见文本 / label / 角色描述（不是 id / class / 编号）；
   `ref` 兜底次数与报告「无可见文字」行数相等。

   ④ 浏览器发起的请求全部源于真实点击（对照 `browser_network` 与操作序列）。

7. **两个开关（F9）与持久化（F11）**：状态行点选 `深度` ⇒ 下一次 run（不带 `traversal`）取 `chain`；显式参数压过开关；中 run 点击只对下一次 run 生效，本 run 的 `traversal` / `mode` 保持起 run 时的定值。**重启后仍生效**（三键落 `settings.json`，见 F11）；键不存在或值非法 ⇒ 回落缺省（关 / `广度` / 由 `btest.readonly` 初始化）。读数以设计档 `docs/design/browser-biz-test.md` §6 的 F9 与 F11 两行为准。

**由该语料直接得出的三条硬纪律**（原提示词草稿缺这三条，必须并入模式卡）：

1. **首开态单列一步**：每个页面/表单，第一次打开就读一次控件与列表——不得假定它与「切换后」一致（17 类全来自这个盲区）。
2. **选值必须读绑定值**：下拉/选择器显示的文字不算证据，读底层值（隐藏输入、组件状态或提交载荷）。
3. **成功提示不算成功**：提交后必须重读列表/台账/单据号；「提示成功但列表没变」在本语料中占 21 + 28 条。
