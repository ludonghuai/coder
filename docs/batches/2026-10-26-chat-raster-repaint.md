### 归因调查（已排除，留档）

- **不是 1.7.2 引入**：`[slow]` 记录 10-22 出现 15 条、10-23 达 108 条，远早于 1.7.2（10-25 打包）。
- **不能证明「以前不卡」**：`lib/diagnostics/frame_watch.dart` 是 2026-10-23 才加的（commit `169a61df`），旧日志零记录 = 当时没测。
- **同一提交修的是另一半**：`169a61df` 修 UI 线程查找（13.7→8.0 ms、卡顿帧 18→0），本轮是 **GPU 光栅化**那一半，没动过。
- **不是 Debug 专属**：Release 同样出现，只是频率低（70 分钟 4 次 vs Debug ~10 次/小时）。

- **2026-10-26 01:12 · 立项范围 = 重绘边界 + 出帧时机，不做列表虚拟化** · 依据：实测慢在 raster（build 0–9 ms），与列表实现无关；结构优化另立一批 · 用户原话：「要起来」 · 时间：01:12

- 既有视觉/交互零变化（粘顶、选择区、滚动锚定、`cacheExtent` 语义）。

### 范围扩到四项（01:30 追加）

用户 01:25 补充症状：「卡的时间大概 2s，很长；并且整个界面会放大占满屏幕，然后缓过来了再缩小」。据此新增两项：

- **F7 切会话不重启内核进程 / 预热真正命中**：当日实读 **38 次 launch · 34 次 warm miss · 0 次 warm hit**，launch→handshake 中位 569 ms，01:16–01:19 三分钟内 13 次启动（最短间隔 0 秒）。这是"切会话卡一下"的直接来源，与 GPU 光栅化是**两个不同的问题**。
- **N3 DPR 变化留痕（诊断）**：本机三显示器、同时存在 **1.5 与 2.25** 两种缩放；「界面突然放大占满再缩回」是缩放因子变化形态，而现有日志 view 0 恒 `@1.5`、无 DPR 变化记录 ⇒ 先加一行打点，重现一次即可定论。

**分诊结论（本轮最重要的一条）**：用户口中的"卡"至少是三种不同成因，此前被混为一谈——
1. 大会话流式 ⇒ GPU 全表面重绘（F5）
2. 失焦仍在渲染 ⇒ 切回时补帧（F6）
3. 切会话 ⇒ 每次重起 Node 进程（F7）
4. 界面放大再缩回 ⇒ 疑似 DPR 变化（N3，待证）
